## 二、数据统一性差距分析

### 2.1 核心问题: 三套配置系统并存

```
问题: 同一类数据分散在三个不同的配置系统

示例: AI模型配置
  ├─ SystemSettings (settings.model区) → api-config.ts → localStorage("yyc3_api_endpoints")
  ├─ ModelProviderPanel → useProviderSlice → localStorage("yyc3_model_providers")
  ├─ VariableCenter (model类) → variable-center.ts → localStorage
  └─ FamilyModelSettings → useFamilySettingsSlice → localStorage

  四个地方都能配AI模型相关的东西！
  它们之间没有同步机制！
```

### 2.2 差距矩阵

| 差距 | 影响 | 严重度 |
|------|------|--------|
| **G1: 模型配置分散** — 4个地方可配模型，互不感知 | 用户在A处改了KEY，B处不知道 | 🔴 严重 |
| **G2: 设置存储不统一** — SystemSettings用api-config.ts，VariableCenter用variable-center.ts，两者独立 | 同一个KEY可能在两处重复定义 | 🔴 严重 |
| **G3: global-store与slices重叠** — global-store有chatSessions，sdk-session-slice也有 | 数据可能不一致 | 🟡 中等 |
| **G4: DataBus未被全面接入** — data-bus.ts设计了统一中枢，但多数页面未使用 | 统一数据层形同虚设 | 🟡 中等 |
| **G5: IndexedDB与localStorage边界模糊** — 什么数据该放哪没有明确规则 | 小数据放IDB浪费，大数据放LS溢出 | 🟢 低 |
| **G6: 编辑反馈不统一** — 部分用toast，部分无反馈 | 用户体验不一致 | 🟢 低 |

## 三、统一方案

### 3.1 目标架构

```
目标: DataBus统一中枢

                    ┌─────────────────┐
                    │   DataBus        │ ← data-bus.ts (已存在!)
                    │   统一调度中枢    │
                    └────────┬────────┘
                             │
              ┌──────────────┼──────────────┐
              │              │              │
        ┌─────▼─────┐ ┌─────▼─────┐ ┌─────▼─────┐
        │ Zustand    │ │ IndexedDB  │ │ Electron  │
        │ Slices     │ │ yyc3_matrix│ │ IPC       │
        │ (轻量配置)  │ │ (大数据)   │ │ (文件/DB) │
        └───────────┘ └───────────┘ └───────────┘
              │              │              │
        ┌─────▼─────────────▼──────────────▼─────┐
        │           所有可编辑页面                    │
        │   通过统一Hook读写，不直接操作存储           │
        └──────────────────────────────────────────┘
```

### 3.2 统一规则

```
规则1: 一个数据域只有一个入口
  模型配置 → 只通过 useProviderSlice
  用户配置 → 只通过 useUserMgmtSlice
  系统配置 → 只通过 useSettingsStore

规则2: 废弃重复配置入口
  SystemSettings的"model"区 → 重定向到 ModelProviderPanel
  VariableCenter的"model"类 → 重定向到 ModelProviderPanel
  global-store的chatSessions → 重定向到 useSDKSessionSlice

规则3: DataBus作为变更通知层
  所有Slice变更 → DataBus.emit()
  所有页面监听 → DataBus.on()
  实现跨页面实时同步
```

### 3.3 具体操作

| # | 操作 | 改动 | 效果 |
|---|------|------|------|
| U1 | SystemSettings"model"区改为跳转链接 | SystemSettings.tsx删model区 | 消除模型配置重复入口 |
| U2 | VariableCenter"model"类改为跳转链接 | variable-center.ts删model组 | 消除模型变量重复入口 |
| U3 | global-store.chatSessions迁移到sdk-session-slice | global-store.ts删chat域 | 消除会话数据重复 |
| U4 | api-config.ts合并到useSettingsStore | api-config.ts改为薄封装 | 统一API配置入口 |
| U5 | 所有Slice变更接入DataBus.emit | 每个Slice的set方法加emit | 实现跨页面同步 |
| U6 | InlineEditableTable所有页面统一使用 | 已统一 ✅ | 无需改动 |

## 四、逻辑互通现状

### 4.1 已互通

| 数据流 | 互通方式 |
|--------|---------|
| ProviderSlice ↔ SDK Chat | useBigModelSDK读取providers |
| ProviderSlice ↔ ModelProviderPanel | 直接CRUD |
| FamilySettings ↔ FamilyModelSettings | slice直接读写 |
| UserMgmtSlice ↔ UserManagement | 直接CRUD |
| IndexedDB ↔ InlineEditableTable | idbPut/idbGet |
| global-store ↔ UnifiedSettingsPanel | 直接读写 |

### 4.2 未互通

| 数据流 | 现状 | 影响 |
|--------|------|------|
| SystemSettings ↔ ModelProviderPanel | 两个独立配置系统 | 模型KEY可能不一致 |
| VariableCenter ↔ 任何其他页面 | 完全独立 | 变量修改不触发其他页面更新 |
| DataBus ↔ 大多数Slice | DataBus已定义但未全面接入 | 跨页面数据不同步 |
| IDE AIChatPanel ↔ useBigModelSDK | 未确认是否接入 | IDE中AI可能无法调用模型 |

## 六、优先修复顺序

```
P0: 消除模型配置重复入口 (U1+U2)
  → SystemSettings model区 → 跳转到 /models
  → VariableCenter model类 → 跳转到 /models
  → 确保所有模型配置只从 useProviderSlice 读写

P1: 统一会话管理 (U3)
  → global-store.chatSessions → 删除
  → 全部使用 useSDKSessionSlice

P2: API配置统一 (U4)
  → api-config.ts → 薄封装，底层走 useSettingsStore
  → SystemSettings network/cluster区 走统一Store

P3: DataBus全面接入 (U5)
  → 每个Slice的set方法后加 DataBus.emit()
  → 需要跨页面同步的组件加 DataBus.on()

P4: IDE AIChatPanel接入SDK (确认)
  → 引入 useBigModelSDK
  → 接通智谱API流式对话
```
